# 推理服务副本规划

## MoE 配方与支持边界

参阅 [2026 大型 MoE 部署参考](MOE_DEPLOYMENT_REFERENCE_2026.md)。`deployment_support` 给出解析支持状态与精确仓库名匹配的上游资料。MoE、特殊结构和未知模型类型不再从旧 TP/PP 搜索获得已批准的候选；旧结果仅保留为 `unverified_capacity_audit`。配方不执行、不替换用户硬件、不证明检查点真实性。普通结构的手填假设仍可解析估算，但不是后端认证。

## 2026-10-13：固定硬件的部署边界

计算资源页面将任务设为“部署”，填写总参数、结构、权重精度、上下文长度（输入+输出）和驻留序列数；固定 GPU 数为 0 时搜索，非零时不擅自加卡。新增的“部署容量边界”与旧逐卡账本共用输入，显示：

- 给定长度、单请求的条件最小 GPU 数，以及目标并发的条件最小 GPU 数。它们是搜索范围与均匀分片假设下的容量候选，不是模型加载认证，更不是速度最优配置。
- 固定配置下，512/2K/4K/8K/32K/128K 及目标长度的驻留序列容量表；超过模型上下文上限的行标为不准入。
- 给定并发可容纳的上下文长度，以及逐卡固定预算、BF16 KV、prefill 激活代理和剩余预算。
- 满足延迟目标的并发仍标为“需压测”。不能把显存上限、排队请求数、在线用户数混为一谈。

当前解析范围是标准全注意力 MHA/GQA/MQA 的 TP/PP；MoE 必须输入总驻留参数，专家映射不在此处认证。MLA、混合/滑窗、状态空间、多模态缓存需要专用适配器；本模块阻断其通用容量外推，不自动猜数。

每 rank 每 token KV 字节：`2(K,V) × 2(BF16 bytes) × (L/PP) × max(1,Hkv/TP) × head_dim`。TP 超过 KV 头数时不继续除小，避免漏掉 KV 复制。每条请求按页向上取整。峰值采用：

`固定账本 + C × ceil(S/page) × page × KV_bytes / 2^30 + max(手填激活, 12×C×S×hidden/2^30)`。

对 C 或 S 做整数二分得到条件上界；C 搜索封顶 65536，S 封顶 10000000 tokens。并发曲线不计共享前缀收益，prefill 全驻留激活代理偏保守；chunked prefill、非均匀层/权重、Graph、媒体编码器、运行时分配都需实测校准。最低卡数沿用原拓扑搜索预算，KV 页边界由新增固定配置账本再次核验。上下文上限默认读取配置，也可手填更低的后端验证上限；0 表示未知，不批准上线参数。

### 稳定性不是一个显存公式

上线前按相同模型版本、精度、GPU/互联、TP/PP、长度分布测试冷启动、图捕获、长 prompt prefill、长输出 decode、并发阶梯、突发到达、取消请求、持续运行和节点故障。记录 TTFT/ITL、端到端 p95/p99、goodput、错误率、峰值显存与 KV 使用量。当前规划器提供检查清单，不声称已执行这些实验。

网关需同时限制单请求输入+最大输出、驻留序列、预留 token 总量及有限队列。健康探测生成通过后才加入路由；流式输出开始后不做透明重试；副本跨真实故障域分布。预热、扩缩容、审计、鉴权和报警是平台工作，不能用 `max_num_seqs` 一项代替。

### 引擎、平台与基础设施边界

vLLM / SGLang 已有推理服务、并行与调度能力，生态中也有部署/路由组件；不能说它们只能单机运行，也不能把引擎进程直接当完整托管平台。参考 [vLLM Kubernetes 部署](https://docs.vllm.ai/en/v0.31.0/deployment/k8s/) 与 [Production Stack](https://github.com/vllm-project/production-stack)。SGLang 的 [服务参数](https://docs.sglang.io/docs/advanced_features/server_arguments)明确区分 KV 静态池与 prefill 调整，并提供 Model Gateway 入口。

云厂商不是必需依赖：自有集群同样可以部署；但 GPU 驱动、通信、网络、持久存储、进程/容器编排和安全运维必须有人负责。Kubernetes 是规模化选择，不是单机试验的强制前提。TessWeave 此次交付的是可解释规划与准入边界，未实现生产级自动故障迁移或 SLA 控制器；Engine 后续应上报实际 KV 容量、峰值、队列与版本，供 Studio 用实测替换代理公式。

实现：`workbench/deployment_envelope.py`；单测：`tests/test_deployment_envelope.py`。不启动服务、不租 GPU、不修改正在运行的引擎参数。

先回答“单个副本装不装得下”，再回答“高峰需要几个副本，坏掉一组机器还能否服务”。两个问题不能用同一个显存除法解决。本模块是可审计的情景计算器，不会租机器、启动部署或自动扩缩容。

## 从容量进入业务负载

打开计算资源，选择本地或云端模型，将任务设为部署，计算候选方案。查看每卡权重、KV、激活及运行时预算，确认后端是否支持所选架构、精度和 TP/PP。下方会出现“业务负载 → 服务副本 → 故障余量”。一个副本可以占多张 GPU；多个副本各自持有完整模型服务能力。

单副本容量未通过时，不进入副本计算。容量通过仍只是估算：必须在真实运行时检查加载峰值、prefill 峰值、decode 峰值和上下文边界。页面显示的 PP 候选不等于部署适配器已经支持多节点 PP 启动。

## 输入代表什么

每日请求是业务请求数；每业务请求调用本模型次数用于描述 Agent、多轮或模型 DAG 的放大。用户数本身不能决定算力。显式峰值 RPS 优先于峰均比，单位仍为业务请求；设为零时使用日均乘峰均比。

平均输入和输出长度用于展示 token 流量需求，不单独推断吞吐。最大输出长度是请求准入上限，不是所有请求的平均输出。长尾样本要进入压测集，不能只测平均长度。p95 首段文本是 HTTP 客户端可测指标，不冒充逐 token TTFT；完整响应时间包括生成过程。

校准项的“单副本联合实测 RPS”必须来自相同模型、权重精度、GPU 型号、TP/PP、长度分布、缓存状态及 SLO 的开环压测。只测 prefill 的峰值和只测 decode 的峰值不能相加当成同一设备的并行能力。先对若干到达率做扫描，选择仍满足目标的观测点，再填入对应 p95 和错误率。零代表未知，不能生成推荐。

目前校准值由用户输入，系统不会伪称已经验证来源。改变模型、拓扑、上下文或 batch 后，会清空旧校准值。JSON 原始结果及 API 调用保存在 Studio 审计链中；`POST /api/serving/plan` 只计算，不执行。

## 把公式代入真实需求

设业务日请求 N，每业务请求调用本模型 c 次，峰均比 k：

`平均模型 RPS = N / 86400 × c`

`峰值模型 RPS = 显式峰值业务 RPS × c`，未提供则为 `平均模型 RPS × k`。

若单副本在目标 SLO 下测得 μ RPS，容量余量 h：

`可用副本能力 = μ × (1 − h)`

`正常副本 R = ceil(峰值模型 RPS / 可用副本能力)`

一个故障域最多放 d 个副本，要求同时失效 f 个故障域后仍满足需求：

`总故障域 = ceil(R / d) + f`

`预配副本 = 总故障域 × d`

`存活能力 = (总故障域 − f) × d × 可用副本能力`

例如 N=100000、c=1、k=10、μ=4、h=20%，需要 4 个正常副本。每故障域放 1 副本，容忍 1 域失效，则预配 5 副本。若每副本 4 GPU，总计 20 GPU。这是代入示例，不是某模型 H100 实测。

故障域可以是整节点、不重叠节点组或可用区；不能把一个节点上的多张卡当成互相独立的高可用副本。跨节点副本共享同一节点时，相关故障超出这个公式的假设。系统显示前 12 个故障域，完整数值保留在表格和 JSON。

## 实验到生产的边界

Engine 仓库的 `tools/benchmark_open_loop.py` 提供恒定/泊松到达率、客户端并发上限、显式丢弃统计、调度延迟及 SLO goodput。首段和总耗时从计划到达时间计算，避免客户端等服务变快才发下一条而掩盖过载。按报告中的 `planner_inputs_for_review` 核对并填值，不能将短时间的单点观测当作持续容量保证。

此版本没有自动路由、健康检查驱动摘除、预热扩容或故障恢复控制器。规划假设同构、已预热且负载均衡的副本；共享网络、存储、长尾分布变化会破坏线性扩展。生产上线还需持续压测、节点故障演练、有限队列、token 配额、观测告警以及滚动升级。已经输出部分 SSE 的请求不可透明拼接重试。

计算实现：`workbench/serving_plan.py`；图形界面：`workbench/static/workspace.js` 的 `servingPlannerView`。单测覆盖缺失输入、SLO 违规、单位校验、调用放大和相关故障域。
